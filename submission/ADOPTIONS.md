# Ecosystem adoptions — what runs, and what does not

The Terminal 3 ADK advertises one SDK across **A2A, ERC-8004, Entra Agent ID, MCP
and Web Bot Auth**. This is the honest catalogue of which of those the Gatekeeper
Agent actually implements.

The rule for this file: an adoption is **shipped** only if it runs — covered by a
test, a live call, or both. Everything else is listed under "not implemented"
with the reason, in its own words, rather than described in a way that reads like
a feature.

Run `node verify.mjs` to exercise every shipped row that does not need a network.

---

## Shipped and exercised

| Adoption | What it does here | Evidence |
| --- | --- | --- |
| **Signed agent card (A2A v1.0 `signatures`)** | The published card carries a detached EdDSA JWS over its RFC 8785 canonical form, signed with the agent's Web Bot Auth key; `kid` is `did:web:gatekeeper-evidence.vercel.app#wba`. `discoverPeer()` now verifies signatures by DID resolution and reports the result beside validation. Change a skill, the endpoint or the security scheme and the signature fails; reorder the JSON and it still verifies. | 11 Node tests + a live test that resolves the kid over did:web and refuses a forged copy |
| **did:web** | `/.well-known/did.json` — `did:web:gatekeeper-evidence.vercel.app`, the same Ed25519 key as the Web Bot Auth directory as a `JsonWebKey2020` verification method (authentication + assertionMethod), and six services: A2A, agent card, MCP, ERC-8004 registration, key directory, status list. Served as `application/did+json`, CORS-open. A test holds did.json and the key directory to the same key. | Node + live |
| **A2A streaming** | `capabilities.streaming: true` and it is real: `SendStreamingMessage` delivers task → working → artifact → completed as server-sent events, from the local server and from the hosted function. Driven by the official client's `sendMessageStream`, by Playwright parsing SSE by hand, and live against `/api/a2a`. | 3 Node + 1 Playwright + 1 live |
| **Signature age, bounded server-side** | The verifier now refuses a signature older than `maxAgeSeconds` from `created`, whatever `expires` the signer chose. The hosted door uses 120 s — because its nonce ledger is per function instance, that is the honest replay window on a serverless host, and it is written down rather than implied away. | 1 Node + 1 live |
| **A2A + MCP, hosted** | `/api/a2a` and `/api/mcp` on gatekeeper-evidence.vercel.app are Vercel functions running the same `createApp()` as `npm run a2a`, deciding with the registered wasm component. The published card is now the v1.0 card the server serves, pointing at that URL; the ERC-8004 registration lists it as an `A2A-JSONRPC` service. Unsigned calls are refused with `401` + `WWW-Authenticate`; a live test signs with the agent's own key, names its own origin, and watches the hosted door resolve the key over the public internet. The deploy root mirrors `agent/` (same lockfile — a test enforces it) and `hosted.test.mjs` walks the static import graph so the credential stack can never be dragged into the function again. | live tests; `agent/src/hosted.mjs`, `api/` |
| **The registered component, hosted in JavaScript (jco)** | `gate-contract/target/…/gate_contract.wasm` — the exact artifact `npm run setup` registers — is transpiled with **jco** into `agent/gate-wasm/`, and `agent/src/gate-wasm.mjs` is the host: a clock, a tenant id, an in-memory KV store and an outbound-HTTP import that refuses. `evaluate` and `spend` run the enclave's real code paths, KV read included, with no Rust toolchain, no enclave and no account. `source.json` records the component's sha256, and a test fails when the release build on disk is not the one the glue was made from. `gate_evaluate` over MCP names which engine answered (`gate_cli` or `component`); binding and idempotency checks stay with `gate_cli`, and the tool says so rather than downgrading. | 11 Node tests, incl. verdict-and-reasons agreement with `gate_cli` case by case; `npm run gate:transpile` |
| **MCP Registry listing** | `agent/server.json` in the official registry's schema (`2025-12-11`), under the GitHub-verified namespace `io.github.PugarHuda/gatekeeper`, naming the npm package this directory publishes (`bin: t3-gatekeeper-mcp`, `mcpName` in package.json, a `files` whitelist that cannot ship `.env`). Validated offline against the vendored schema with ajv. Publishing is two commands (`npm publish`, `mcp-publisher publish`) on the owner's accounts — see MAINTENANCE.md. | 4 Node tests |
| **Accessibility, measured (axe-core)** | `qa-console/a11y.test.mjs` runs axe-core (WCAG 2.1 AA + best practice) through Playwright over the evidence site and the QA console, idle and after a verdict. Serious/critical violations fail; the first run found one (scrolling screenshot frames unreachable by keyboard) and it was fixed. Part of `node verify.mjs`. | 3 Playwright tests |
| **security.txt (RFC 9116)** | `/.well-known/security.txt` on the evidence site: contact, expiry, canonical URL, policy. Served as `text/plain`; a test refuses an expired file. | live |
| **A2A Agent Card** | `agent/agent-card.json` — name, skills, DID, endpoints, trust (TDX + BBS+), in A2A `AgentCard` shape. | live at `/.well-known/agent-card.json` |
| **A2A × Web Bot Auth — who may call** | The A2A endpoint shipped with `noAuthentication`. Now every JSON-RPC call must carry a web-bot-auth signature: the server reads `Signature-Agent`, fetches that origin's `/.well-known/http-message-signatures-directory`, resolves `keyid`, verifies method + authority + path + body digest + expiry, and refuses a nonce it has seen before the signature's own expiry. The card declares the scheme (`HTTPSig`) so a peer learns to sign before its first call is refused. The caller's identity is its origin plus keyid — nothing shared in advance. | official A2A client with a signing fetch, 6 refusal tests, Playwright by hand |
| **MCP over Streamable HTTP** | The same origin serves MCP at `/mcp` — stateless, one server per request as the SDK documents, JSON responses — behind the same signature check. This is the *remote* adoption path: an MCP host anywhere points at the URL. Driven by the official MCP client over HTTP and by hand-written JSON-RPC from Playwright; an unsigned client is refused. | 5 Node + 5 Playwright |
| **A2A server (protocol v1.0)** | `npm run a2a` — a JSON-RPC endpoint on the **official `@a2a-js/sdk`**, serving `evaluate-gated-action` and `bind-credential` as A2A tasks. A peer with only our URL discovers the card, picks a transport, sends a message and reads a task back: submitted → working → completed, with the verdict as an artifact. A rejected action *completes* the task with decision `rejected` — no is an answer. The v1.0 card is generated from the published card, and `validateAgentCard` now understands v1.0's `supportedInterfaces` (it called every v1.0 agent unreachable before). | 12 Node tests driving the **official A2A client** over HTTP |
| **A2A discovery** | `discoverPeer(origin)` fetches `/.well-known/agent-card.json` over HTTP and validates it. A peer needs only the domain — nothing shared in advance. | 8 Node tests against a real server |
| **A2A capability exchange** | Two agents establish trust by exchanging a BBS+ **capability credential** with selective disclosure: prove one capability, hide the manifest. | `npm run demo:a2a`, 2 Node tests |
| **Web Bot Auth (RFC 9421)** | Every approved action's outbound request is signed with Ed25519, including an RFC 9530 `Content-Digest` over the body, plus the profile's `expires` and `nonce`. **Verified both ways against Cloudflare's reference implementation** (`web-bot-auth` on npm): our signatures pass their verifier with the key resolved from our published JWKS, and their signatures — including the `signature-agent` component we never emit — pass ours. Before this our signatures carried no `expires`, and the reference verifier refuses those outright. | 22 Node tests (8 interop) + a live round trip |
| **Web Bot Auth key directory** | The Ed25519 JWKS is published at `/.well-known/http-message-signatures-directory` with the RFC media type, so any destination can verify with no prior exchange. | live-site tests |
| **W3C Bitstring Status List v1.0** | Credential revocation published as a gzipped 131,072-entry bitstring and checked over HTTPS. No chain, no gas — this is the revocation path that actually runs. | 21 Node tests; `npm run status-list` |
| **ERC-8004 identity — minted** | **Agent #201** on the reference IdentityRegistry on Sepolia (`0x7177a686…`), tx `0x37965ccd…`, block 11581941. `agentURI` resolves to a conformant `registration-v1` file the site serves — the register script fetches and validates that document before it will send, because a mint pointing at the A2A card would have registered an identity every resolver rejects. `npm run erc8004` reads the whole loop back live: registry → token → URI → document → `registrations[201]`. | on chain; `npm run erc8004` live; 7 Node tests on the file |
| **ERC-8004 reputation** | The Reputation Registry read for agent #201. The reference deployment **predates the EIP's final interface** — checked by selector, it lacks `getSummary`, `readAllFeedback` and the final `giveFeedback`, and has `getClients` / `getLastIndex` / `readFeedback` — so the aggregate is computed from the per-client reads that exist, and the preflight prints what is absent instead of letting "missing revert data" stand in for an answer. It reports zero feedback for #201, because there is none. `getIdentityRegistry()` names our identity registry back: the pair is matched. | `npm run erc8004`, live |
| **T3 host activity ledger** | `activity.log` — the node's per-call record (contract, function, outcome, sequence number, hash) — read back and tallied; `execute_action` successes and errors kept apart; the agent's claimed dispatches reconciled against it as a necessary condition, not a verdict. The documented `audit.get-mine` is read beside it and has stayed empty through 39 dispatches (bug #29). | `npm run audit`, live; 9 Node tests |
| **`http-with-placeholders`** | The contract routes any body carrying `{{profile.*}}` markers through the PII-safe outbound interface, so the host substitutes the investor's data and the plaintext never enters the component. **Proven live**: `{{profile.first_name}}` is delivered (HTTP 200 via `http-with-placeholders`); `{{profile.no_such_field_xyz}}` comes back `placeholder_unknown` from the host — it really consulted the profile. | `npm run prove:enclave`, live; Rust tests for the routing rule |
| **In-TEE outbound HTTP (`http`)** | The enclave performs the approved call itself, in the same invocation as the decision. | live, HTTP 200 |
| **Enclave-held broker credential** | The mandate names a key in `z:<tid>:secrets`; the enclave reads it after approving and puts `Authorization: Bearer …` on the outbound call. The agent never holds it. **Proven live**: the diagnostic path with no credential gets HTTP 401 from `httpbin.org/bearer`; `execute_action` against the same URL gets 200, with a request input that carried no header. | `npm run prove:enclave`, live; 6 Rust |
| **Egress authorisation** | `agent-auth-update` grant scoped to contract, functions and destination hosts; an ungranted host is refused by name. | live |
| **Stateful velocity limit** | Cumulative spend held in the enclave's own KV across invocations, with the window derived from the cluster clock rather than supplied by the caller. | live 3-spend test |
| **Idempotent dispatch** | A caller-chosen key; a retry replays the recorded outcome instead of placing a second order. **Proven live**: the second call under the same key returns `dispatched: false, replayed: true` with the first call's response byte for byte. | 5 Rust + 2 Playwright + `npm run prove:enclave` live |
| **Credential/action binding** | The agent commits to which credential it verified *and which action for*; the enclave recomputes that commitment from the action it is about to perform. | 8 Rust + 12 Node cross-language conformance |
| **Deny-by-default mandates** | Amount cap, assets, kinds, counterparties, per-payee sub-limits, trusted issuers, validity window, expiry. An empty mandate approves nothing. | 47 Rust tests |
| **MCP server** | The agent *as* an MCP server over stdio: `gate_evaluate`, `bind_credential`, `check_credential_status`, `discover_agent`, `resolve_erc8004_agent`, `check_erc8004_registry`, `fetch_paid_resource`, `gate_execute`, plus two resources. This is the distribution story — a host adds one line of config and gets the mandate gate. | 19 Node tests driving a **real MCP client** over stdio |
| **Node discovery** | `npm run discover` reads the node's own inventory with an **agent key** over plain HTTPS — no session, no wasm, no credits: which core contracts it runs and at what version, our contract as the node describes it, and this agent's delegation verdict. Version drift on the node is what has broken this project hardest (bugs #12, #19); this makes it one command instead of an autopsy. | 3 Node tests + live |
| **x402 — settled on chain** | `npm run x402:settle`: a local paywall wired the way x402 is meant to be — the *resource server* verifies and settles through the public facilitator at `x402.org`, the agent only signs — moved **0.01 USDC on Base Sepolia** from the payment wallet to the ERC-8004 owner wallet, through the mandate. Facilitator tx `0x52b164d133…`, block 46058792, broadcast by the facilitator (the payer paid no gas). The script then checks the chain rather than the receipt: the `Transfer` log in the tx, and both balances at explicit block tags — because the first run read "latest" from a lagging public RPC and saw nothing move while the log said otherwise. `--tx <hash>` re-checks without paying. | on chain; `npm run x402:settle -- --tx …` |
| **x402 (HTTP 402 payments)** | A 402's payment requirement becomes an `Action` and goes through the same mandate. Only on approval is an EIP-3009 `TransferWithAuthorization` signed (real EIP-712) and the request retried. Verification recovers the payer with ecrecover — the facilitator's `/verify` minus the balance read — and the EIP-712 domain is checked against the deployed token's own `DOMAIN_SEPARATOR()`, so "a settlement contract would accept this" is verified rather than asserted. | 28 Node tests + 6 Playwright over real HTTP; `npm run x402:verify` live |

## Not implemented, and why

Listed so nobody has to infer it from silence.

| Adoption | Why not |
| --- | --- |
| **ERC-8004 reputation — writing** | Reads run (above). Nothing is *written*: feedback about this agent is for its counterparties to leave, not for it to leave about itself. |
| **In-contract `vp.verify`** | Attempted and blocked by the host: importing `host:interfaces/vp` registers fine, then 500s on every invoke (bug #7). Without it the enclave cannot verify a BBS+ proof itself — see STATUS_AND_ROADMAP §3.1 for exactly what that costs. Re-checked 2026-08-27: the repro contract was reverted in June, so the finding stands on the June evidence and would cost a fresh registration to re-stage. |
| **On-chain revocation registry** | Needs a deployed contract and gas. The `revoke_vc` code path is written and tested with an injected registry, and the status list above covers the same need without a chain. |
| **AP2 / agentic-commerce rails** | **Not implemented**, and we now think AP2 is the wrong target here. No AP2 message format is produced or consumed, so calling it an adoption would be a claim about a resemblance rather than about code. x402 was built instead, because it can be exercised end to end against a real counterparty. See the row below for what we found while looking. |
| **`tee:agent-connect` (T3's own commerce rails)** | **Attempted, and blocked by the platform — not a design choice.** The node serves `tee:agent-connect@1.4.0`, undocumented (bug #26). It is the natural home for this gate: deciding whether an intent may be confirmed is exactly `commerce-intent-confirm`. Every caller-facing function fails on a user-profile envelope the *host* assembles, missing a `kind` field that `tee:user`'s profile writer refuses as an unrecognised key — **bug #27**. There is no caller-side workaround; we tried every channel the SDK exposes. Repro: `node t3-qa/core-contracts-probe.mjs`, which is written to fail if it ever starts working. |
| **`tee:vc` OpenID4VP holder stack** | **Attempted, and blocked.** `tee:vc@2.6.0` carries `submit-vp` — a real DCQL/OpenID4VP request that answers `unsatisfied: query could not be satisfied with available credentials`, i.e. the node really is matching the query against credentials it holds — plus `my-presentations` (`{"presentations":[]}`) and `issue-credential`. This is the holder-side derive our June bug #3 said did not ship: it does, on the node, undocumented. Issuing into it needs `keys.generic_api` metadata; the one documented way to write keys accepts every shape **silently**, returning a real `txHash`, and the consumer still calls it missing — **bug #28**. Same repro script. This remains the most promising route to closing our biggest correctness gap, and it is one platform fix away. |
| **Entra Agent ID** | Not implemented. Listed by the ADK; nothing here talks to it. |
